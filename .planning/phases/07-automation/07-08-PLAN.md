<objective>
Implement D-13 step two: the per-role **Publish** button. For one role, in this order —
PUT/POST that role's automatic Computer Group with a freshly generated "exactly one of N logged
on" relevance (D-09/D-10), refresh that role's Task (07-07's `ensureRoleTask`), POST a new
policy `SingleAction` targeting the group with reapply-daily settings (D-11), then stop the
role's previous Open action — with each step's success or failure surfaced separately.

Purpose: this is the step that actually changes what the fleet does, and it is deliberately
per-role so publishing one role can never disturb another's live targeting.

**Sequencing rationale (RESEARCH Pitfall 4 and Pitfall 7 / Open Question 1, decided in plan
07-04):** Group first, because the worst case of a Group-succeeds-then-Task-fails is that the
already-running previous action simply re-evaluates against an updated membership rule — the
least disruptive failure mode. The action is created **before** the previous one is stopped, so
a failure between those two steps leaves two idempotent actions running rather than zero
(`Assign-RoleMapping.ps1`'s D-12 upsert makes a duplicate run harmless; having no action at all
would silently stop mapping the role).

Output: a working Publish flow plus unit coverage of the step ordering, the settings, and the
empty-list behaviour.
</objective>

**`publishRole(role)`** — the D-13 step-two orchestration, replacing the no-op stub plan 07-06
left on the Publish button:
1. Clear the role's `errEl`/`resultEl`, disable its Publish and Save buttons, reset
   `publishState[role].stepStatus`.
2. **Guard:** if `roleState[role].dirty` is true, refuse to publish and tell the operator to
   Save first — the audit store must record the membership that is about to go live (NFR-03),
   so Publish must never run against unsaved edits. Surface this inline; it is not an error
   state, it is the D-13 two-step contract.
3. `ensureRoleGroup` → on error stop, mark `[1/4 Group] FAILED`, leave later steps untouched and
   explicitly tell the operator the Task and action are unchanged.
4. `ensureRoleTask` (07-07) → on error mark `[2/4 Task] FAILED` and state that the **group is now
   updated but the Task is stale**, so the operator knows exactly what is out of sync.
5. `deployRolePolicyAction` → on error mark `[3/4 Action] FAILED` and state that the group and
   Task are updated but the previous action is still the live one.
6. `stopPreviousRoleActions(role, newActionId, …)` → mark `[4/4 Stop]` with the count stopped, or

7. On full success write a single summary line into `resultEl`:

   set `publishState[role].lastPublishedOn`, and re-enable the buttons.
Every step's status is written into `publishState[role].stepStatus` as well as the DOM, and each
step's message is prefixed with its `[n/4 Name]` label. Steps run **sequentially via callbacks**
(IE9: no Promises, no async/await). No `alert()` anywhere.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| dashboard → `computergroups/custom` | Defines live membership evaluation for the whole fleet |
| dashboard → `POST actions` | Deploys code that runs as SYSTEM on every matching endpoint |
| dashboard → `POST action/{id}/stop` | Terminates live fleet automation |
| generated relevance → BES client relevance engine | Untrusted usernames become client-evaluated targeting |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-07-08-01 | Elevation of Privilege | An empty or malformed username list producing fleet-wide group membership | mitigate | `buildRoleGroupRelevance`'s literal `false` guard (plan 07-04) is exercised end-to-end here; Task 3 asserts the emitted `<ComputerGroup>` CDATA is exactly `false` and contains no `logged on users` clause for an empty role, and that a supplied scope group cannot override the guard. |
| T-07-08-02 | Spoofing | Policy action silently applying to zero computers | mitigate | `SingleAction` with client-evaluated `<CustomRelevance>member of group …` only — `SourcedFixletAction` is absent from the file and asserted at zero occurrences (SKILL.md §3, RESEARCH Pitfall 2). |
| T-07-08-03 | Tampering | 400 Bad Request from `<Target>` placed before `<Settings>` | mitigate | Element order is fixed inside the plan-07-04 builder and asserted by index comparison in Task 3 (SKILL.md §3, RESEARCH Pitfall 3). |
| T-07-08-04 | Repudiation / Integrity | A partial publish leaving Group, Task and action out of sync with no operator awareness | mitigate | Sequenced least-disruptive-first (Group → Task → Action → Stop); each step reports a distinct `[n/4 Name]` status naming exactly which objects are now stale; `publishState[role].stepStatus` retains the outcome for the Analysis tab (plan 07-09). |
| T-07-08-05 | Denial of Service | Unbounded accumulation of Open policy actions per role | mitigate | `stopPreviousRoleActions` stops every Open action matching the role's title except the newly created one, on every Publish — the create-new-then-stop-old ordering means a mid-sequence failure leaves two harmless idempotent actions, never zero. |

| T-07-08-SC | Tampering | npm/pip/cargo installs | accept | No package-manager installs in this phase — RESEARCH.md § Package Legitimacy Audit records "Not applicable". |
