<objective>
Build the D-06 periodic drift-check job: a root-server PowerShell scheduled task that, for every
role in the `RolePublish.db` audit store, rebuilds the "exactly one of N logged on" relevance
from that role's current username snapshot and re-PUTs the role's automatic Computer Group when
the live relevance differs.

Purpose: D-06 is a locked decision. The dashboard's Publish flow is on-demand and not
transactional (RESEARCH Pitfall 4) — a group can be left stale by a half-completed Publish, a
console operator hand-editing the group, or a REST 5xx. This job is the safety net that makes
the audit store, not the group's relevance text, the actual source of truth (D-05).

**Discretion decisions recorded here (CONTEXT § Claude's Discretion):**
- **Mechanism:** a root-server PowerShell scheduled task, not a BigFix policy action — the work
  is pure REST + SQLite on one host and has no reason to run on endpoints (RESEARCH Pattern 4).
- **Cadence:** daily at 04:00 local. That is after the content pipeline's existing 03:00 window
  so the two never contend, and it matches the daily reapply cadence D-11 gives the policy
  action.
- **Credential:** `Get-BigFixCredential.ps1` (AKeyless universal identity, built in the prior
  07-00 work and still live). This is the one place in this phase that legitimately needs a
  service credential; the dashboard rides the operator's console session instead.

Output: a pure relevance module, the driver, a Pester suite, a cross-language golden fixture,
and the scheduled-task registration.
</objective>

Flow:
1. Import `scripts/RoleGroupRelevance.psm1`. Abort with a distinct exit code if
   `RolePublish.db` or `sqlite3.exe` is missing.
2. `SELECT DISTINCT Role FROM RolePublishRun` (filtered by `-Role` when supplied).
3. For each role: `Get-CurrentRoleUsers` → `New-RoleGroupRelevance` → the expected relevance.
4. Find the role's group by title (`$GroupTitlePrefix + $role`) via
   `GET $BESRootUrl/api/computergroups/custom/<urlencoded site>` and a title match on the
   returned XML. If no group exists, log `[MISSING] <role>` and **do not create one** — group
   creation is the dashboard's Publish responsibility (D-13); this job only corrects drift.
5. `GET $BESRootUrl/api/computergroup/custom/<site>/<id>`, extract the
   `SearchComponentRelevance/Relevance` text, and compare to the expected relevance after
   normalising CDATA wrapping and surrounding whitespace only (no case folding — the generator
   already lower-cases what it should).
6. If they differ, `PUT` the same endpoint with a freshly built `<ComputerGroup>` document using
   the same element set plan 07-04 settled on, and log `[DRIFT-FIXED] <role>` with a short
   before/after excerpt. If they match, log `[OK] <role>`.
7. Per-role failures are caught, logged as `[FAIL] <role> <status>`, written to the Windows Event
   Log with a dedicated event id in the existing 80xx range (use 8050), and **do not abort** the
   remaining roles — same discipline as `Publish-RoleSnapshot.ps1`.
8. Write one run summary JSON next to the existing pipeline logs (same directory convention as
   `Invoke-ContentSync.ps1`) recording per-role outcome counts, and exit non-zero only if every
   role failed.
9. Under `-WhatIf`: perform all GETs and comparisons, log what it would PUT, issue no PUT.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| audit store (`RolePublish.db`) → generated BigFix relevance | Stored usernames become an executable relevance expression pushed to a live Computer Group |
| scheduled task → BES REST API | Runs unattended as a service principal with an AKeyless-sourced operator credential |
| AKeyless vault token file → script | A path to a credential, read but never written |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-07-05-01 | Elevation of Privilege | Drift job PUTting an over-broad relevance onto a live group | mitigate | `New-RoleGroupRelevance` carries the same empty-list `false` guard as the dashboard, asserted against the hand-authored golden fixture; the job never creates a group (only corrects an existing one), so it cannot invent new targeting. |
| T-07-05-02 | Tampering | Relevance injection via a stored username | mitigate | `"` → `""` escaping inside `New-RoleGroupRelevance`, unit-tested; usernames were already parameterized on the way in by 07-03. |
| T-07-05-03 | Tampering | SQL injection via `-Role` on the membership query | mitigate | `Get-CurrentRoleUsers` passes `@role` through `Invoke-SqliteCommand -Parameters`; no string concatenation into SQL. |
| T-07-05-04 | Information Disclosure | Operator password exposure in logs or on disk | mitigate | Credential obtained at runtime via `Get-BigFixCredential.ps1` (AKeyless universal identity, no secret at rest — the 07-00 design); the scheduled-task Arguments string carries no credential, asserted by the Task-3 acceptance criteria; run logs record role names and statuses only. |
| T-07-05-05 | Denial of Service | A single failing role aborting the whole sync | mitigate | Per-role try/catch → `[FAIL]` log + Event 8050 + continue, mirroring `Publish-RoleSnapshot.ps1`; the run exits non-zero only if every role failed. |
| T-07-05-06 | Repudiation | Silent unattended changes to live groups | mitigate | Every corrected group emits `[DRIFT-FIXED] <role>` with a before/after excerpt into the per-run JSON log; the audit store already records who published the underlying membership. |
| T-07-05-SC | Tampering | npm/pip/cargo installs | accept | No package-manager installs in this phase — RESEARCH.md § Package Legitimacy Audit records "Not applicable". |
</threat_model>
